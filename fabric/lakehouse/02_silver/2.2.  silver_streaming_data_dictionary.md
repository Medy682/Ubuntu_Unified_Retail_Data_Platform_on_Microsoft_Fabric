# Silver Streaming Data Dictionary

## Overview

The Silver Streaming layer contains cleaned, standardized, validated, and enriched streaming data produced from the Bronze streaming layer using PySpark Structured Streaming.

Unlike the batch Silver layer, which processes static Bronze Delta tables using PySpark DataFrames, the streaming Silver layer continuously processes incoming Bronze streaming data using Streaming DataFrames.

### Streaming Architecture

```text
Event Simulator
      ↓
Fabric Eventstream
      ↓
Bronze Streaming
      ↓
PySpark Structured Streaming
      ↓
Silver Streaming
      ↓
Gold / Real-Time Analytics
      ↓
Power BI
```

The Silver Streaming layer provides a continuously refined representation of retail events for downstream real-time analytics and Gold-layer transformations.

---

# Silver Streaming Tables

## 1. silver.silver_streaming_events

### Description

Unified Silver streaming table containing cleaned, standardized, validated, deduplicated, and enriched retail events.

The table is populated continuously from:

`bronze.bronze_streaming_events`

using PySpark Structured Streaming.

### Schema

| Column | Data Type | Description |
|---|---|---|
| `event_type` | string | Type of retail event, such as `product_view`, `cart_action`, `checkout_start`, `purchase_success`, or `inventory_update`. |
| `event_timestamp` | timestamp | Timestamp representing when the retail event occurred. Converted from the original ISO-8601 string format. |
| `customer_id` | string | Unique identifier of the customer associated with the event. |
| `product_id` | string | Product identifier associated with the event. |
| `product_description` | string | Description of the product associated with the event. |
| `country` | string | Country associated with the customer/event. |
| `session_id` | string | Session identifier for events where session information is available, primarily product-view events. |
| `view_duration_seconds` | long | Duration of a product view in seconds. NULL for events where this attribute is not applicable. |
| `EventProcessedUtcTime` | timestamp | Timestamp recorded when the event was processed by the streaming ingestion process. |
| `PartitionId` | long | Partition identifier associated with the streaming event. |
| `EventEnqueuedUtcTime` | timestamp | Timestamp representing when the event was enqueued in the streaming infrastructure. |
| `event_key` | string | SHA-256 hash generated from event attributes and used as the implementation key for streaming deduplication. |
| `event_date` | date | Calendar date derived from `event_timestamp`. |
| `event_hour` | integer | Hour of day derived from `event_timestamp`. |
| `processing_delay_seconds` | long | Difference in seconds between event occurrence time and processing time. |

# Event-Specific Attributes

The streaming Bronze layer contains two types of data structures:

1. Event-specific Bronze tables used to persist the individual event types.
2. A unified Bronze streaming table, `bronze_streaming_events`, used as the source for the unified Silver streaming table.

### Event-Specific Bronze Tables

The following event-specific Bronze tables are implemented:

- `bronze_fact_cart_actions`
- `bronze_fact_checkout_starts`
- `bronze_fact_inventory_updates`
- `bronze_fact_product_views`
- `bronze_fact_purchases`

All five event-specific Bronze tables currently use the same standardized schema:

- `event_type`
- `event_timestamp`
- `customer_id`
- `product_id`
- `product_description`
- `country`
- `invoice_id`
- `quantity`
- `unit_price`
- `total_order_value`

Although these tables represent different event types, the current implementation does not maintain a separate schema containing unique attributes for each event type. Instead, the same standardized set of columns is used across all five event-specific Bronze tables.

### Unified Bronze Streaming Table

The `bronze_streaming_events` table contains the common streaming event attributes together with Product View-specific attributes and streaming ingestion metadata:

- `event_type`
- `event_timestamp`
- `customer_id`
- `product_id`
- `product_description`
- `country`
- `session_id`
- `view_duration_seconds`
- `eventprocessedutctime`
- `partitioned_id`
- `eventenqueuedutctime`

### Unified Silver Streaming Table

The `silver_streaming_events` table is derived from the unified Bronze streaming data. It retains the Bronze streaming attributes and adds Silver-layer derived and processing metadata:

- `event_type`
- `event_timestamp`
- `customer_id`
- `product_id`
- `product_description`
- `country`
- `session_id`
- `view_duration_seconds`
- `eventprocessedutctime`
- `partitioned_id`
- `eventenqueuedutctime`
- `event_key`
- `event_date`
- `event_hour`
- `processing_delay_seconds`

The Silver streaming table therefore provides a standardized unified representation of the streaming events. The current implementation does not propagate `invoice_id`, `quantity`, `unit_price`, or `total_order_value` from the event-specific Bronze tables into `silver_streaming_events`.

If these attributes are required for downstream streaming analytics in the future, they can be incorporated into the Silver model or exposed through dedicated event-specific Silver tables.

# Streaming Silver Transformation

The Silver Streaming transformation is implemented using PySpark Structured Streaming.

The transformation process includes:

1. Reading the Bronze streaming Delta table as a Streaming DataFrame.
2. Standardizing data types.
3. Trimming string values.
4. Applying data quality filters.
5. Configuring event-time processing.
6. Applying a watermark.
7. Generating an implementation event key.
8. Deduplicating streaming events.
9. Deriving analytical attributes.
10. Writing the transformed stream to the Silver Delta table.

---

# Data Type Standardization

The Bronze `event_timestamp` column is initially stored as a string.

It is converted to a Spark `timestamp` type in the Silver layer.

String-based attributes are also trimmed to remove unnecessary leading or trailing whitespace.

This produces a more consistent schema for downstream analytical processing.

---

# Data Quality Standards

The streaming Silver transformation applies validation rules to incoming events.

The following fields are required:

- `event_type`
- `event_timestamp`
- `customer_id`
- `product_id`
- `country`

Records failing these required-field checks are excluded from the Silver Streaming table.

For `view_duration_seconds`:

- NULL values are permitted when the field is not applicable to the event type.
- Negative values are rejected.
- Zero or positive values are accepted.

This allows the pipeline to distinguish between legitimately missing event-specific attributes and invalid values.

---

# Event-Time Processing

The pipeline uses `event_timestamp` as the event-time column.

Event time represents when the retail activity actually occurred rather than when the event was processed by the streaming infrastructure.

The streaming data also contains:

- `EventEnqueuedUtcTime` — when the event was enqueued.
- `EventProcessedUtcTime` — when the event was processed.

Keeping these timestamps allows the platform to distinguish between event occurrence time, enqueue time, and processing time.

---

# Watermarking

A 10-minute watermark is applied to `event_timestamp`.

The watermark is used to support event-time processing while limiting the amount of state that Spark needs to maintain for stateful streaming operations.

```python
.withWatermark("event_timestamp", "10 minutes")
```

The watermark provides a tolerance for late-arriving events and helps bound streaming state used by operations such as:

- Windowed aggregations
- Streaming deduplication
- Stream-stream joins

The watermark does not simply mean that every event arriving more than 10 minutes late is automatically rejected. Its primary purpose is to manage state and determine how long Spark should retain information for event-time processing.

---

# Streaming Deduplication

The Bronze streaming data does not contain a dedicated globally unique `event_id`.

Therefore, the Silver transformation creates an implementation key called `event_key`.

The key is generated using a SHA-256 hash derived from a combination of event attributes, including:

- `event_type`
- `event_timestamp`
- `customer_id`
- `product_id`
- `session_id`
- `country`

The resulting key is used for streaming deduplication:

```python
.dropDuplicates(["event_key"])
```

### Important Design Consideration

`event_key` is an implementation-level deduplication key and is not guaranteed to be globally unique.

In a production environment, the preferred design would be for the source system or event producer to generate a unique `event_id` for every event.

---

# Derived Analytical Attributes

The Silver Streaming transformation creates additional analytical fields.

### event_date

Derived from `event_timestamp`.

Used to support:

- Daily analysis
- Date filtering
- Aggregations
- Time-based reporting

### event_hour

Derived from `event_timestamp`.

Used to support:

- Hourly event analysis
- Traffic pattern analysis
- Real-time activity monitoring

### processing_delay_seconds

Calculated as the difference between `EventProcessedUtcTime` and `event_timestamp`.

This provides an indication of the processing delay between event occurrence and processing.

# Streaming Timestamp Metadata

The Silver Streaming table preserves multiple timestamp perspectives:

| Timestamp | Purpose |
|---|---|
| `event_timestamp` | Actual event occurrence time. |
| `EventEnqueuedUtcTime` | Time the event was enqueued by the streaming infrastructure. |
| `EventProcessedUtcTime` | Time the event was processed. |

These timestamps enable analysis of:

- Event-time behavior
- Streaming latency
- Processing delays
- Late-arriving events

# Streaming Data Lineage

The streaming Silver data follows the lineage below:

```text
event_simulator.py
        │
        │ Retail JSON events
        ▼
Fabric Eventstream
        │
        │ Streaming ingestion
        ▼
bronze.bronze_streaming_events
        │
        │ PySpark Structured Streaming
        │
        ├── Type standardization
        ├── String trimming
        ├── Data quality validation
        ├── Event-time processing
        ├── 10-minute watermark
        ├── Event key generation
        ├── Streaming deduplication
        └── Derived analytical attributes
        │
        ▼
silver.silver_streaming_events
        │
        ├── Real-time analytics
        ├── Gold-layer transformations
        └── Power BI
```

### Source

`event_simulator.py` generates realistic retail events and sends them to the Fabric streaming endpoint using the Azure Event Hubs protocol.

### Ingestion

Fabric Eventstream receives the streaming events and writes them to the Bronze streaming layer.

### Bronze

`bronze.bronze_streaming_events` stores the unified incoming event stream in Delta format.

Event-specific Bronze tables are also maintained for event-specific attributes:

- `bronze_fact_product_views`
- `bronze_fact_cart_actions`
- `bronze_fact_checkout_starts`
- `bronze_fact_purchases`
- `bronze_fact_inventory_updates`

### Silver Processing

PySpark Structured Streaming continuously reads the Bronze streaming table and applies:

- Standardization
- Validation
- Event-time processing
- Watermarking
- Deduplication
- Analytical enrichment

### Silver Output

The resulting data is written to:

`silver.silver_streaming_events`

The Silver Streaming table serves as a downstream source for real-time analytics and Gold-layer transformations.

# Streaming Silver Write Configuration

The streaming Silver table is written using a Delta sink with checkpointing.

The checkpoint location is:

```text
Files/checkpoints/streaming_silver
```

The stream uses append output mode and a 10-second processing trigger.

Conceptually:

```text
Bronze Streaming
      ↓
PySpark Structured Streaming
      ↓
Delta Streaming Sink
      ↓
Silver Streaming
```

Checkpointing allows Spark to maintain streaming progress and recover the streaming query after interruptions.

# Streaming Silver Readiness

The Silver Streaming layer is considered ready for downstream use when:

- Bronze streaming events are being ingested successfully.
- The Structured Streaming query is active.
- New Bronze records are continuously processed.
- Data quality rules are applied.
- Event timestamps are standardized.
- Event-time processing is configured.
- Watermarking is enabled.
- Duplicate events are handled.
- Analytical attributes are derived.
- Silver records are continuously written to Delta.
- Streaming checkpoints are maintained.
- Downstream analytics can consume the refined streaming data.

The Silver Streaming layer therefore provides a continuously refined and analytics-ready representation of the retail event stream.
