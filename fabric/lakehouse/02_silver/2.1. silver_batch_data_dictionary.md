# Silver Data Dictionary

## Overview

The Silver layer contains cleaned, standardized, validated, and transformed
datasets produced from the Bronze layer using PySpark.

The `02_silver_transformation` notebook loads 13 Bronze datasets and writes
13 corresponding Silver Delta tables. The transformation workflow includes:

- Bronze schema and data inspection
- NULL and blank/whitespace validation
- Duplicate detection and handling
- Data type validation and conversion
- Identifier format validation
- Business-rule validation
- Foreign-key validation
- Text standardization
- Invalid-record handling where required
- Silver DataFrame validation
- Silver Delta table writing and post-write verification

The Silver layer preserves the Bronze ingestion metadata columns
`_source_file`, `_ingestion_timestamp`, and `_ingestion_date` for lineage and
auditability.

# Silver Tables

## 1. `silver.silver_customers`

**Purpose:** Customer master data from the Ubuntu Retail Group source system.

| Column | Data Type | Description |
|---|---|---|
| `customer_id` | string | Unique customer identifier. Primary key. |
| `customer_unique_id` | string | Persistent customer identifier associated with the customer. |
| `customer_zip_code_prefix` | integer | Customer ZIP-code prefix. |
| `customer_city` | string | Customer city. |
| `customer_state` | string | Customer state code. |
| `_source_file` | string | Bronze source-file path used for ingestion. |
| `_ingestion_timestamp` | timestamp | Timestamp when the record entered Bronze. |
| `_ingestion_date` | date | Date when the record entered Bronze. |

### Silver transformation

- Trims leading and trailing whitespace from applicable string attributes.
- Casts `customer_zip_code_prefix` to integer.
- Preserves the validated `customer_id`, `customer_unique_id`, and customer state values.
- Preserves ingestion metadata.

### Validation

- NULL validation
- Blank/whitespace validation
- Duplicate `customer_id` validation
- ZIP-code validation
- ZIP-code range inspection
- Customer state validation
- Row-count and schema validation

**Foreign key:** `customer_id` is a parent key and is referenced by downstream datasets; it is not a foreign key in this table.

## 2. `silver.silver_order_items`

**Purpose:** Individual product items belonging to customer orders.

| Column | Data Type | Description |
|---|---|---|
| `order_id` | string | Order associated with the item. Foreign key to `silver_orders`. |
| `order_item_id` | integer | Item sequence number within the order. |
| `product_id` | string | Product associated with the item. Foreign key to `silver_products`. |
| `seller_id` | string | Seller associated with the item. Foreign key to `silver_sellers`. |
| `shipping_limit_date` | timestamp | Seller shipping deadline. |
| `price` | decimal(12,2) | Item price. |
| `freight_value` | decimal(12,2) | Freight/shipping value. |
| `_source_file` | string | Bronze source-file path. |
| `_ingestion_timestamp` | timestamp | Bronze ingestion timestamp. |
| `_ingestion_date` | date | Bronze ingestion date. |

### Silver transformation

- Trims `order_id`, `product_id`, and `seller_id`.
- Casts `order_item_id` to integer.
- Casts `shipping_limit_date` to timestamp.
- Casts `price` to `decimal(12,2)`.
- Casts `freight_value` to `decimal(12,2)`.
- Preserves ingestion metadata.

### Validation

- NULL/blank validation
- Duplicate/composite-key validation
- Price and freight business-rule checks
- Shipping date validation
- Foreign-key validation against orders, products, and sellers

# Silver-Layer Data Quality Standards

## NULL Validation

Required and applicable columns are checked for NULL values before and/or
after transformation.

## Blank / Whitespace Validation

Applicable string fields are checked for empty or whitespace-only values.

## Duplicate Validation

Primary identifiers and relevant composite keys are checked for duplicates.

Where duplicates represent invalid records, the transformation removes them
using `dropDuplicates()`.

Examples include:

- `order_id` in Orders
- `(order_id, payment_sequential)` in Payments
- exact duplicate rows in POS transactions
- `review_id` in Reviews

## Identifier Format Validation

Identifiers are validated against the expected source-system formats, including:

- 32-character hexadecimal Ubuntu Retail Group identifiers
- `EMP_#####`
- `STR_###`
- `PRM_###`
- `SUP_####`

## Type Standardization

Silver transformations explicitly standardize data types where required,
including:

- integer
- decimal
- double
- timestamp
- date
- boolean
- string

## Business-Rule Validation

Business rules include:

- Non-negative ZIP codes
- Valid review scores from 1 to 5
- Non-negative payment values
- Valid promotion discount range
- Non-negative inventory values
- Inventory status consistency
- Valid employee/store/supplier/promotion identifier formats
- Valid supplier tiers

## Referential Integrity

Foreign-key relationships are validated using left-anti joins against the
corresponding parent Silver tables.

## Row-Count Reconciliation

Bronze and Silver row counts are compared after each transformation where
appropriate. When records are intentionally removed because they are invalid
or duplicate, the notebook documents the resulting change.
